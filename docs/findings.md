# Findings — evidence first, diagnosis second

Everything below is read from `results/tables/*.csv` (generated by `python -m analysis`); the raw
`result.json` files under `results/raw/` carry the per-rank timings, NCCL's own transport report
and the counters. Hardware: two NVIDIA GB300 trays in one NVLink domain, rack 3uwoq/6g3ya,
2026-09-30. Each tray: 4 GPUs (NVLink NV18 between them), 4 ConnectX-8 rail VFs; **a rail VF is a
multi-plane port — four physical 200 Gb/s planes (`rdma_p0..p3_rail<N>`) = 800 Gb/s** — even though
sysfs `rate` and `ethtool` report a single plane's 200 Gb/s (the counter arithmetic below is what
exposed this: a single rail carried 411 Gb/s). NIC and GPU both negotiate PCIe Gen6 x16; each GPU
reaches its NIC through the Grace socket (`nvidia-smi topo -m`: NODE, not PXB), i.e. GPUDirect over
C2C. Software: the NGC PyTorch container (torch
2.8.0a0, CUDA 13.0, NCCL 2.27.7), k3s 1.36, Cilium 1.20, NVIDIA GPU Operator 26.7 in DRA mode.

## 1. Baseline — all-reduce vs message size, three transports (E1)

| observation | evidence |
|---|---|
| Multi-node NVLink reaches **835 GB/s** bus bandwidth at 8 GiB; the curve is still rising past 1 GiB | `e1_size_vs_transport.csv`; NCCL report: 256 `P2P/MNNVL` channels, 0 `NET/*` |
| The four RDMA rails plateau at **≈ 410–425 GB/s** from 256 MiB up | 640 `NET/IB/…/GDRDMA` channels, 0 `NET/Socket`, GID index 7 on every rail |
| TCP over the overlay: **4 GB/s**; TCP over one rail's IPVLAN child: **118 GB/s** | `NET/Socket` channels; same wire as the RDMA run |
| Below ~8 MiB every transport is latency-bound: 1 MiB takes ~82 µs on both NVLink and RDMA (`e1_small_latency.csv`) | per-iteration CUDA events on every rank |
| Per-rank spread is < 1 % almost everywhere; the slowest rank moves around (no fixed straggler) | `rank_variance` in every sweep row |

Why the curve rises: an all-reduce of *S* bytes over *n* ranks costs a fixed latency term (kernel
launches, handshakes, one round trip per ring step) plus *S·2(n−1)/n / bandwidth*. At 1 MiB the
fixed term dominates and busbw is tens of GB/s regardless of the wire; past a few hundred MiB the
wire dominates and the transports separate by an order of magnitude each.

Two anomalies are recorded, not smoothed: RDMA at 1 GiB (246 GB/s, a single run) and a 15 % rank
spread at 32 MiB. Both sit at NCCL protocol/algorithm switch points and are repeat-worthy.

## 2. Diagnosis — where the ceiling is (E2 + counter windows)

| observation | evidence |
|---|---|
| RDMA bus bandwidth scales with rails: **96 / 207 / 364 GB/s** at 1 / 2 / 4 rails (4 GiB) | `e2_rails.csv` |
| The bytes on the wire equal the theoretical minimum for a two-node all-reduce (S per direction): one rail carried **411 Gb/s transmit and 412 Gb/s receive at the same time** for algbw 50 GB/s; four rails **~482 Gb/s each way, each** for algbw 235 GB/s | `e5_counters.csv`; sysfs `port_xmit_data` ×4 verified byte-for-byte against `ethtool tx_vport_rdma_unicast_bytes`; `port_rcv_data` likewise |
| Link rates are quoted per direction (`200 Gb/sec (2X NDR)` = 2 lanes × 100 Gb/s each way), so a rail is **not** a 200 Gb/s link: 411 Gb/s cannot cross one, and 965 Gb/s bidirectional through one rail rules out "800 bidirectional" too. The rail is a 4-plane 800 Gb/s-per-direction port (1.6 Tb/s bidirectional); it ran at **51 % (1 rail) to 60 % (4 rails)** of that in each direction | `rdma_p0..p3_rail<N>` netdevs, 200 Gb/s each |
| GPUDirect off (`NCCL_NET_GDR_LEVEL=0`): algbw falls from ~235 to **145 GB/s** while the rails carry the same bytes; the GPU-side PCIe counters stay flat in both cases — on GB300 the GPU reaches host memory over C2C, so the host bounce costs time, not GPU PCIe bytes | `e5_sensitivity.csv`, `e5_counters.csv` |
| The NVLink run leaves the rails idle and moves ~240 GB/s per GPU on NVLink instead | `e5_counters.csv` (`nvlink_tx_GBps_total` vs `rail_xmit_Gbps_total`) |
| No congestion signal on the rails during any window: CNPs, ECN marks, out-of-sequence, sequence errors and ACK timeouts stay at zero per second | `e5_counters.csv` |

**Diagnosis, kept apart from the evidence.** Bus bandwidth tracks the rail count linearly, so
each rail brings its own ceiling of ~410–480 Gb/s, about 55 % of its 800 Gb/s. That ceiling is
*not* the wire (utilisation) and *not* congestion (flat DCQCN counters), and *not* PCIe (Gen6 x16 on
NIC and GPU, ~120 GB/s per direction against ~60 GB/s used). What remains is the per-rail injection
path: one NCCL network connection per GPU–NIC pair with its proxy thread, and a GPUDirect route that
crosses the Grace socket over C2C (`NODE` in the topology matrix). That is a hypothesis with the
evidence narrowed to it, not a proof; the next experiment is more NCCL channels per NIC
(`NCCL_MIN_NCHANNELS`, `NCCL_NCHANNELS_PER_NET_PEER`) and a GPU-to-NIC placement check, not a
network change. Cross-tray NVLink at 835 GB/s is ~2× the four rails together — the topology decides
which path a collective takes, and the path decides the ceiling.

## 3. Scaling — the DDP workload (E3)

GPT-124M, bf16, 8 × 1024 tokens per GPU per step, DDP with the default 25 MiB buckets.

| GPUs | placement | samples/s | efficiency | comm fraction |
|---|---|---|---|---|
| 1 | one tray | 381 | 100 % | 0 % |
| 2 | one tray | 710 | 93 % | 6 % |
| 4 | one tray | 1191 | 78 % | 78 % |
| 8 | two trays, NVLink | 2804 | 92 % | 70 % |
| 8 | two trays, RDMA | 2090 | 69 % | 91 % |

(`e3_scaling.csv`; "comm fraction" is NCCL kernel residency over step time from `torch.profiler`,
which overlaps with backward compute — it is an upper bound on exposed communication.)

Where accelerator time is lost: the step is ~21 ms of compute for ~474 MiB of fp32 gradients, which DDP
all-reduces in about 19 buckets of the default 25 MiB. That bucket size sits at the knee of the E1 size
curve — already bandwidth-sensitive, but with the per-collective fixed cost still a third of each call —
so the step depends on both the wire and the number of collectives. Same bucket size across transports
isolates the wire (92 % vs 69 %); same transport across bucket sizes (E5, 25 → 200 MiB) isolates the
per-collective cost (+32 %). Over the rails, the gradient exchange becomes the step. The
1→4 GPU drop on one tray (93 % → 78 %) is the same effect intra-tray plus the launch overhead of a
small model — not the network. Evidence separated from diagnosis: the network is *not* the problem
on one tray (no NIC is involved); over two trays the transport is the difference (92 % vs 69 %).

## 4. The optimization — Baseline → Hypothesis → Change → Measurement → Conclusion (E4)

- **Baseline.** RDMA path, 4 rails, GPUDirect on, `NCCL_IB_QPS_PER_CONNECTION=1` (NCCL's default): 98 / 413 / 408 GB/s at 16 MiB / 512 MiB / 4 GiB, 5 repeats each (`e4_before_after.csv`).
- **Hypothesis (written before the run).** One queue pair per NCCL connection serialises each peer flow; more QPs, with `NCCL_IB_SPLIT_DATA_ON_QPS=1`, would spread a message over parallel flows and raise large-message bandwidth. Expected trade-off: more out-of-order delivery (`out_of_sequence`) and per-QP state.
- **Change.** `NCCL_IB_QPS_PER_CONNECTION` 1 → 2 → 4 (+ split); nothing else touched; 5 repeats per cell.
- **Measurement.** QPs=2: −4 % / −9 % / −8 % (p = 0.006 / < 0.001 / 0.29). QPs=4: **−19 % / −32 % / −29 %** (p < 0.001 at every size). Repeat-to-repeat spread within a cell is ≤ 2 % except one 4 GiB outlier.
- **Conclusion — negative, and useful.** The hypothesis was reasonable: the counter windows show each rail at ~55 % of its 800 Gb/s with one QP per connection, so there *is* headroom on the wire. But more QPs did not reach it: the counter window at QPs=4 shows each rail at 338 Gb/s instead of 482, with `out_of_sequence`, CNP and ECN counters still at zero — so the loss is not reordering or congestion, it is the sender doing less useful work per unit time (splitting every message across QPs shrinks each work request and multiplies completions). The knob helps where a single flow cannot fill a link (ECMP across spines, adaptive routing); on a rail-optimised two-tray path it only adds overhead. Keep the default, and look for the ceiling on the injection side (channels per NIC, GPU–NIC placement) rather than in the transport's QP count. The measurement, not the folklore, decides.

## 5. Sensitivity appendix (E5)

| knob | result |
|---|---|
| `NCCL_BUFFSIZE` 4 MiB / 16 MiB (default 4 MiB) | within noise of the baseline at every size |
| GPUDirect off | −38 % at 4 GiB; same bytes on the rails, 1.6× the time: the host bounce over C2C is pure latency/copy cost |
| `NCCL_ALGO=NVLS` vs `Ring` on NVLink | NVLS 474 vs Ring 388 GB/s algbw at 4 GiB — the NVSwitch reduction is what makes the NVLink curve keep climbing |
| `NCCL_ALGO=Tree` | not a valid configuration: NCCL has no Tree implementation for all-gather (used by the topology exchange); recorded as a configuration result |
| TCP with `NCCL_SOCKET_NTHREADS=4`, `NCCL_NSOCKS_PERTHREAD=4` | 16.8 vs 2.4 GB/s algbw — 7× on the socket path, still 14× below RDMA |
| DDP `bucket_cap_mb` 25 → 200 over the rails | **2090 → 2769 samples/s (+32 %)**, comm fraction 91 % → 32 %: fewer, larger all-reduces amortise the per-collective cost on the slower transport |

The last row is the production lever: when the interconnect is the bottleneck, change how often
you talk before changing how you talk.

## 6. Extending to production multi-node GPU systems

- The manifests scale by `nnodes`; one pod per tray, one GPU claim and one rail claim per pod. The
  IPVLAN + shared-netns design keeps every host inventory check green while pods use the rails.
- The counters watched here become alert rules: a fabric cell with `NET/Socket` channels is a FAIL,
  not a slow run; CNP/ECN rates and `out_of_sequence` per rail are the congestion signal; a rail
  below its share of line rate during a known-good collective is a rail fault.
- Placement follows topology labels (NVLink clique, fabric block): inside a domain use MNNVL, between
  domains budget for the rails and choose bucket sizes / accumulation accordingly.
- Floors are calibrated per width and message size (bus bandwidth is not width-invariant); the sweep
  here is the reference shape for that calibration.
